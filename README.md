# spec-flow

Spec-Flow is a Codex plugin for release-centered Spec-Driven Development. It records product strategy and release decisions in a consuming project's `.specs/` directory, then uses a local controller to validate document dependencies, approval receipts, execution evidence, and recovery.

The intended path is **strategy → release → verified implementation**. The strategy path is **constitution → design → roadmap**; design coordinates applicable shared architecture, infrastructure, and structure documents. Each explicit SemVer release has its own spec, plan, and tasks. A release may contain several stories or features.

## Workflow

| Stage | Skill | Canonical artifact or result | Gate |
| --- | --- | --- | --- |
| Product direction and agile project framework | `$constitution` | `.specs/constitution.md`: purpose, beneficiaries, measurable outcomes, scope, principles, authority, resources, risks, delivery/learning, completion, and approval | Human direction for unknown decisions; registry approval before dependent work; execution retains separate authorization |
| Shared system design | `$design` | Separate applicable `.specs/{architecture,infrastructure,structure}.md` documents and their templates; system design, execution/operations, and repository organization with annotated trees | Existing gate for each document kind; constitution and actually used sources approved before dependent writing; no mandatory chain; roadmap records justified N/A |
| Outcomes and release projections | `$roadmap` | `.specs/roadmap.md`: measurable outcomes, horizons, canonical releases and synchronized version table | Approved strategy; explicit `vX.Y.Z` projections; human selection of the next release is separate from planned status and execution authorization |
| Release behavior and acceptance | `$specify` | `.specs/release-vX.Y.Z/spec.md`: scope, canonical stories/criteria, traceability/examples/quality tables, and measurement | Explicitly selected release from the approved roadmap; resolve material questions and reconcile references before plan |
| Optional clarification of approved behavior | `$clarify` | Dated section in the same `spec.md`: question/decision/application and pending/routing tables | Current approval of the spec and its dependencies at entry; drafts stay with specify; amended content needs new approval and explicit downstream adoption |
| Technical implementation plan | `$plan` | `.specs/release-vX.Y.Z/plan.md`: canonical phases/table, change scope, capacity, risks, and verification coverage | Approved spec/applicable design; coherent phases and planned AC/quality coverage; blockers resolved before tasks |
| Executable task decomposition | `$tasks` | `.specs/release-vX.Y.Z/tasks.md`: canonical tasks, synchronized task/coverage tables, explicit files, steps, and checks | Approved plan/spec; coherent references, complete AC coverage with final checks, resolved blockers; task approval and execution authorization are distinct |
| Optional documentary coherence review | `$analyze` | Conversation report with examined-source, planned coverage/sufficiency, and finding/correction tables | Current approved spec/plan/tasks and sources; full-release validation and analyze gate; failed controls or CRITICAL findings block recommending implementation; no writes or execution authority |
| Incremental implementation | `$implement` | Observable increments, current acceptance/regression evidence, independent phase review, and validated phase commits | Current approvals, scoped execution authorization, native host prerequisites, and sufficient retained context; partial contributions and final acceptance remain distinct |
| Technical convergence | `$converge` | Conversation assessment with AC coverage, integrated evidence, findings, and canonical handoff | Current approvals/evidence and reviewed phase commits; `technical_complete=true` enables assessment; all applicable obligations demonstrated and zero findings required to confirm |
| Outcome review and learning | `$review-release` | Conversation report, supported generated closure snapshot/reference, and follow-up through the planned measurement source | Current confirmed convergence; pending impact allowed; one final audit commit; later observations preserve the historical closure |
| Branch finishing and integration | `$finishing-branch` | Conversation trace from the original audit checkpoint to the actual branch/PR/integrated result; publication/deployment reported separately | Valid source closure and explicit action/destination authority; preserve original commits and verify the resulting state; respect destination rules and separate publication/deployment scope |

`$clarify` and `$analyze` are recommended side channels for ambiguity and consistency; `$backlog` independently captures, refines, and maintains deferred opportunities. `$using-spec-flow` coordinates consultation, documentary editing, execution, and resumption from observed state and existing authority. Recommended design elaboration is **architecture → infrastructure → structure**, using only applicable documents. Inspect existing repository organization and operational constraints early; findings can require revising an earlier decision. Pin the approved constitution and only the design sources actually used, with no reciprocal dependency cycles. Structure can proceed without infrastructure when it does not rely on it; infrastructure does not require structure by default. Omitting a dependency does not mean its document is inapplicable. Document genuine N/A in the roadmap under its own gate.

The bootstrap's mode, routing, resumption, decision-owner, and conversation-handoff tables identify intent, actual project/release context, examined evidence, blockers, next owner/action, and authority. Consultation creates no files and performs no initialization, migration, repair, or execution, including on unadopted/legacy projects. Authorized edits retain adoption and owner gates; execution retains its full native protocol and scoped authorization. Resumption distinguishes documentary drafts, active/interrupted runs, and closure checkpoints, preserving revisions, agent/attempt identity, reviewed commits, and history. Existing valid choices/permissions are reused within scope; missing decisions remain explicit. Bootstrap does not approve/rewrite canonical artifacts or add a controller kind, gate, coordination file, or status registry. Owner skills keep their specialized instructions and evidence requirements.

Backlog is optional plain Markdown with one current BNNN register row, progressive ID-linked notes, and a significant-decision history. Preserve provenance, P0–P3 ordering, provisional unspecified priority, discard/merge/reopening reasons, and real release/spec/US/AC destinations without deleting items. Capture requires no approved strategy or release; consultation/read-only review writes nothing and does not initialize or migrate. Authorized writes retain adoption/migration controls. A projection, approved roadmap selection, and valid draft incorporation are different facts; Incorporated proves neither approval nor delivery. Partial incorporation keeps the residual opportunity explicit. Roadmap/spec/plan/tasks and controller evidence retain their decisions and gates; backlog has no controller document kind, approval receipt, or phase gate and cannot defer an approved obligation or authorize scope/execution/closure.

Architecture covers context, quality scenarios, components/contracts, data, runtime behavior, and significant decisions. Infrastructure maps components to execution resources and documents configuration/access, delivery, operations, capacity/costs, and recovery where applicable, including local host requirements. Structure maps responsibilities to paths, defines placement/dependency rules, and shows a verified annotated file/directory tree plus a separate proposed tree when changes are needed. All three distinguish proposals and approved design from verified implementation, retain decision rationale and amendment history, and link details rather than duplicating them.

`$design` is the single entry for creating, revising, or reviewing those perspectives. A scoped request updates only affected documents; a read-only coherence review reports findings without writing. Its three templates live in `skills/design/assets/`. The controller retains the separate `architecture`, `infrastructure`, and `structure` kinds/gates and approval receipts; `design` is not a runtime kind or another project document. Existing document paths, digests, approvals, and dependencies remain valid when their content is unchanged. Use `$design` with the desired perspective in place of the former three skill invocations; historical records retain their original references.

The roadmap links stable outcome IDs and measurements to progressively detailed horizons and explicit release projections. A result may span several releases; later opportunities may remain unversioned. Its version table must mirror the canonical `releases` array's versions, order, objectives, and statuses, adding horizon, capabilities, and selection context. The skill explicitly reviews that coherence; the controller does not validate the Markdown table. A planned/projected version is not automatically selected. Confirm the next version with the user and retain all downstream gates; release delivery alone is not evidence of impact. Review priorities with scoped evidence, agreed cadence/triggers, and approval of substantive changes.

The release spec links real user value and roadmap outcomes to bounded stories, observable acceptance, quality, and relevant error/compatibility behavior. Stories and acceptance remain canonical JSON records; readable traceability, example, and NFR tables reference them. The specify skill reviews table membership/ownership and semantic coherence; the controller does not inspect those Markdown views. Quality obligations needing task coverage must be represented in canonical ACs, directly or by NFR reference. Resolve scope/acceptance/feasibility blockers before plan, leaving appropriate technical choices to it. Spec defines behavior/acceptance, plan the delivery solution, and tasks concrete actions/checks. Full-release AC coverage and separate execution authorization remain required.

Clarification distinguishes initial drafts, current approved specs, and amendment drafts. Resolve unapproved drafts through specify under its own gate; clarify's phase gate requires approval of the spec itself and its dependency closure. Ask up to five consequential questions per round, one at a time; unanswered blockers remain visible and prevent planning. Its template stays inside spec.md, recording confirmed answers and sources, applied canonical changes, pending decisions, and routing without another editable requirements registry. Synchronize stories/ACs and affected examples/quality tables, obtain approval of the final revision, and explicitly adopt downstream bases. Historical receipts do not approve changed content; preserve active-run reconciliation and closed-release evidence.

The implementation plan describes verifiable increments, technical choices, change scope, realistic resources/forecasts, risk validation, delivery preparation, and review/adaptation. Its phase table mirrors canonical `phases` IDs, order, descriptions, and dependencies, adding story/AC context; coverage tables distinguish partial contributions from final verification. The plan skill reviews table coherence and semantic coverage because the controller does not inspect those Markdown views. Keep per-task actions/commands in tasks, preserve current single-implementer/review requirements, and keep execution authorization distinct from document approval, reusing it only within its approved scope.

Task decomposition produces bounded, relevant, verifiable work with explicit file scope, ordered steps, and observable closure. Its task map mirrors canonical `tasks`; the coverage matrix links all ACs to contributing tasks and actual final-verification steps while distinguishing partial contributions. The skill reviews table/contract coherence and semantic sufficiency; the controller checks structure and nominal AC coverage. Task packets discard tasks.md prose/tables, so execution-critical instructions must live in canonical fields or approved governing sources actually retained in context. Keep full-release coverage, evidence-based progress, phase reviews/commits, and separate scoped execution authorization.

Analyze reviews the approved release's documentary preparation without changing files, approvals, progress, or execution state. It checks strategic/design alignment, canonical/table coherence, meaningful planned coverage of acceptance and quality, and instructions retained for execution. Its report records actual sources/bases, controller results, coverage and justified findings; incomplete or failed entry remains diagnostic-only. Initial setup, migration, correction, approval recording, and downstream adoption belong to separate owner workflows. Zero findings is valid within the reviewed scope and is not execution authorization or evidence of implemented behavior; converge and review-release retain their distinct responsibilities.

Implementation builds small scoped changes with relevant checks during construction, then verifies and reviews actual behavior before closing tasks. Sol distinguishes partial contributions from final AC fulfillment, checks integrated behavior/regressions, and uses `refresh-evidence` when later changes stale completed-task checks; refresh does not reopen implementation or bypass phase review/commit. Aligned Luna/Sol/reviewer roles retain exact result fields, attestation, attempt limits, recovery, and authorization. Reports identify observed capability, evidence, blockers, and commits without a second progress registry. Final technical completion hands off to converge, then release review and finishing-branch; local phase commits alone do not establish CI into main, publication, or measured impact.

```text
.specs/
├── constitution.md
├── architecture.md         # when applicable
├── infrastructure.md       # when applicable
├── structure.md            # when applicable
├── roadmap.md
├── backlog.md              # optional
└── release-v2.0.0/
    ├── spec.md
    ├── plan.md
    └── tasks.md
```

## Adoption and approvals

On a new project, initialize the controller before writing canonical documents. A project with legacy `.specs/NNN-feature-name/` folders must run the migration preview and apply workflow before new Spec-Flow writes. Migration requires a committed snapshot of the exact originals, explicit feature-to-release mapping, and reviewed candidate documents. Old `Status: Approved` text and checked boxes do not become authority or verification by themselves; only identifiable, verifiable historical records can be imported. See [migration.md](plugins/spec-flow/harness/contracts/migration.md).

Use the portable CLI as `python3 -B <plugin-root>/scripts/spec-flow.py --root <project> OP --input <json-file>`. The [shared controller operations](plugins/spec-flow/harness/contracts/operations.md) maintain invocation, query safety, adoption, validation, and approval/revision mechanics for all skills. Each skill retains its HARD-GATE, semantic checks, and authority boundary. Approval receipts pin normalized decision content and its dependency closure; derived progress alone does not invalidate approval. Execution authorization remains scoped to a release and phases, separate from merge, push, publication, or deployment.

New nonlegacy projects use `initialize` with `{}` before authorized writing; legacy projects use reviewed migration. Strict consultation creates no files and excludes `complete`/check-complete because their Git checks can refresh the index and the wrapper uses a temporary input. Report recorded closure as historical and current completion as not revalidated; authorized owner workflows retain mandatory live checks. The [canonical contract](plugins/spec-flow/harness/contracts/canonical-contract.md) defines document fields, including roadmap `releases` and plan `phases`; reading tables remain synchronized views reviewed by their owning skill.

## Native Codex execution

The runtime uses Python standard library and POSIX file locks (`fcntl`); Windows is not currently supported. Verification in this development environment uses Python 3.14.4 and Git 2.54.0. Production implementation requires an isolated linked Git worktree, writable Git common-directory ownership registry, native Codex delegation tools, and readable host session logs. The actual orchestrator must be attested **Sol high**; one **Luna high** implementer works on a scoped task at a time; a distinct **Sol high** reviewer checks the integrated phase before its commit. Python enforces contracts and records evidence; it does not launch models or infer their identity from a supplied model name. If a host capability or attestation is unavailable, execution stops with a diagnostic and no automatic model substitution.

The default invocation covers one authorized phase. Each task needs current verification against the actual worktree and Sol review. The first Luna attempt may receive at most two targeted corrections. A phase closes only after an independent review of its stable staged tree and a matching validated commit. On interruption, inspect the active native agent and worktree, then resume or reconcile the existing attempt before retrying; a lost final message does not justify replay. The controller keeps compact audit records and an audit checkpoint after the last code phase. See the [execution contract](plugins/spec-flow/harness/contracts/execution.md) and [Codex adapter](plugins/spec-flow/harness/adapters/codex/README.md).

The bundled `PreToolUse` hook is a limited reinforcement for supported `apply_patch`/`Edit`/`Write` inputs after the user trusts it. The handler consults the same release validators and execution registry as the controller, resolves the Git common-directory ownership record, and checks supported write paths against the active task scope without relying on the branch name. It does not select skills, inspect all write methods, or replace the controller's release approval and evidence gates. Treat a hook allow as no proof of authorization.

Development candidate `ef7897d` passed [E7 native evaluation](docs/implementation/e7-ef7897d.md) and [E8 isolated installation](docs/implementation/e8-ef7897d.md) on the evaluated host. E8 used a separate marketplace/plugin identity, preserved 113 package resources, discovered 14 enabled skills in a fresh app-server client, and passed 127 plugin tests plus 9 hook tests from the installed cache. The existing stable installation and configuration were unchanged after cleanup. These results apply to the tested candidate and stated scenarios; they do not publish a new release, prove automatic catalog refresh in existing chats or live hook activation, or establish time or cost savings. See the [evaluation history](docs/implementation/harness-progress.md) for earlier candidates.

## Install from GitHub marketplace

The stable marketplace points to GitHub `main`:

```bash
codex plugin marketplace add santiago-migoni/spec-flow --ref main
codex plugin add spec-flow@spec-flow
```

This installs the package from the marketplace source, not from a local checkout. Start a new Codex chat to discover the installed skills. The local test package should use a separate, uniquely named marketplace so it cannot replace an existing installation. A release version change and its changelog heading are separate from feature changes.

## Ecosystem

Spec-Flow can coexist with [Ponytail](https://github.com/DietrichGebert/ponytail) and [RTK](https://github.com/rtk-ai/rtk); neither is required.
