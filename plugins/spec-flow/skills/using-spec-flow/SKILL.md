# Spec-Flow: using-spec-flow

<HARD-GATE>
Inspect project configuration and `.specs` first. If legacy `.specs/NNN-name/` folders exist, stop before writing and follow the actual `migrate-preview` → human review → `migrate-apply` flow in [the migration contract](../../harness/contracts/migration.md); resume an interrupted apply with `migrate-resume`. There is no `migrate` CLI operation. For a new unadopted project, run `initialize` with empty JSON input `{}` first. Run the runtime gate for the intended document or execution phase and obey it; using-spec-flow itself is not a gate kind. Urgency never waives a failed gate.
</HARD-GATE>

Strategy: `constitution → applicable shared system design → roadmap`. Delivery: `specify → clarify (optional) → plan → tasks → analyze (optional) → implement (verified phases and commits) → converge → review-release → finishing-branch`. Create architecture, infrastructure, and structure documents only when applicable to planned releases; record N/A with a reason in the roadmap when inapplicable. Strategy files are `.specs/{constitution,architecture,infrastructure,structure,roadmap}.md`. An active release uses `.specs/release-vX.Y.Z/{spec,plan,tasks}.md` and may contain multiple stories. Release identifiers use strict numeric SemVer such as `v2.0.0`.

Recommended design elaboration order: architecture → infrastructure → structure. This is not a mandatory dependency chain. Inspect existing repository organization and operational constraints early; revise earlier decisions when findings require it. Each document pins the approved constitution and only approved design sources actually used; do not introduce reciprocal pins. Infrastructure does not require structure by default; structure can proceed without infrastructure when it does not rely on it. Navigational links alone do not imply dependencies, and omitting a dependency does not make its source document N/A. Do not create future dependent documents to complete an earlier one.

Architecture owns context, quality scenarios, components/contracts, data/runtime behavior, and significant design decisions. Infrastructure owns execution resources, delivery/operations, and recovery, including local host needs when applicable. Structure maps responsibilities to paths and placement/dependency rules, with an annotated verified tree and a separate proposed tree when needed. Keep proposals, approved design, and implementation evidence distinct; approval does not prove deployment or implementation.

At session start inspect configuration and `.specs`, then call `status --input <json-file>` using `{}` and `gate --input <json-file>` for the intended phase. For release gates pass `{"kind":"<phase>","release":"vX.Y.Z"}`. Do not infer authorization from file existence, legacy `Status: Approved` tables, checked boxes, or urgency. Existing approved sources can be reused only while content digest and scope remain current. If approved sources change during an open run, reconcile any active native agent and use `abandon` with a recorded reason and authorization before starting a new run; unchanged completed-task evidence is reused only when its exact task contract, source pins, checks, and code fingerprint still match. Attempt limits carry across abandoned runs. Legacy projects use the documented preview/apply/resume operations before new writes; new projects run `initialize` with empty JSON input `{}`.

The constitution establishes product direction and the agile project framework: purpose, beneficiaries, measurable outcomes, boundaries, principles, authority, resources, risks, delivery/learning, and completion criteria. Its approval does not itself authorize implementation. Roadmap owns measurable outcomes, priorities, horizons, and release projections; detailed team working agreements are linked rather than duplicated.

Roadmap's version table mirrors the canonical releases array's versions, order, objectives, and statuses, adding horizon, capabilities, and selection context. The roadmap skill reviews table coherence; the controller does not validate that Markdown view. Outcomes can span several releases and distant opportunities may remain unversioned. Planned/projected entries do not establish human selection or authorize specification/execution. Confirm the next explicit version with the user, keep the table and selection section consistent, and require the approved roadmap and downstream gates. Retain existing controller statuses; do not use active just to mark selection. Reference release review evidence without treating delivery as observed impact.

Specify turns the selected release into bounded user value, scope, canonical stories/acceptance, quality, and outcome measurement. Its traceability, example, and NFR tables reference those canonical records; the skill reviews coherence because the controller does not validate Markdown views or semantic completeness. Reflect quality/error/compatibility obligations requiring task coverage in canonical ACs, directly or through explicit NFR references. Resolve material scope/acceptance/feasibility questions before plan; appropriate technical choices remain with plan. Spec owns behavior/acceptance, plan solution/phases/verification strategy, and tasks actions/files/concrete checks. Full-release AC coverage and independent execution authorization still apply.

Clarify is optional and its phase gate requires current approval of the spec itself and its dependency closure. Initial unapproved specs and interrupted amendment drafts resolve questions through specify under its own gate, retaining R00 or the existing draft RNN. Do not approve a draft just to enter clarify or treat the old receipt as approval of edits. Clarify asks up to five consequential questions per round, one at a time; remaining blockers prevent planning. Its dated section inside spec.md records confirmed answers/sources, canonical changes, pending questions and routing in two tables. Update canonical stories/acceptance and affected views, gain approval of the final amendment, and explicitly adopt affected downstream bases. No second requirements/approval registry or execution authority is created; preserve active-run reconciliation and historical closure.

Plan translates the approved spec into verifiable increments, technical choices, change scope, capacity/forecasts, risks, operational delivery preparation, and verification coverage. Its phase table must mirror canonical phases IDs/order/descriptions/dependencies, and its reference matrices preserve US/AC/NFR ownership with partial versus final verification explicit. The plan skill reviews those Markdown views and feasibility; the controller validates structural phase contracts and later task coverage. Resolve plan blockers and gain approval before tasks; logical independence does not waive single-implementer, phase review/commit, or separate execution authorization requirements.

Tasks decomposes the approved plan into bounded executable work with explicit files, ordered steps/checks, and observable closure. Its task map mirrors canonical tasks and its coverage matrix preserves AC ownership, all contributing tasks, and existing final-verification steps. The skill reviews coherence and sufficiency beyond structural/nominal controller checks. Task packets omit tasks.md prose/tables: keep execution-critical instructions in canonical fields or approved governing sources actually retained in context. Resolve blockers, validate full-release coverage, and gain task approval before execution; generated progress, single-implementer/phase review requirements, and distinct reusable execution authorization remain authoritative.

Implement and its three role instructions connect small scoped construction/checks with partial versus final acceptance, semantic expected/observed review, integrated behavior/regressions, and current evidence. Use `refresh-evidence` for affected completed tasks when later changes stale their checks; it does not reopen work or bypass phase review/commit. Preserve exact result fields, native attestation, one Luna, three-attempt limits, and recovery before replay. Reports derive from evidence rather than a second progress registry. After final `complete.technical_complete`, hand off to converge, then review-release and finishing-branch; phase commits alone do not imply CI into main, publication, or measured impact.

Converge assesses the integrated release in conversation using canonical AC/story ownership, partial versus final verification, referenced quality conditions, and applicable shared/delivery decisions. Current controller completion enables the semantic assessment; confirmation also requires every applicable obligation demonstrated and zero findings, including LOW. Missing evidence is Not verifiable; justified N/A cannot discard approved obligations. Route exact proposed changes to canonical owners and reconcile approvals/execution before implementing them; optional opportunities do not automatically become tasks. Converge writes no spec marker or generated closure note: review-release owns the combined derived outcome and final audit commit.

Review-release separates the rich conversation report (capabilities/feedback, outcome measurement, delivery, limitations, lessons and proposals), the controller's supported closure snapshot, and later measurement follow-up. Require the corresponding confirmed convergence as well as current controller evidence. Observed impact means usable observations, not achieved targets or complete measurement; pending/unavailable impact alone need not block technical closure. release-review persists only its existing technical/phase, impact/evidence and delivery fields, writes the generated roadmap reference and one final audit commit, and releases ownership; it does not save the full narrative or revise canonical release statuses. Later evidence goes to the planned measurement source and subsequent approved decision updates, not a rewritten closure or another closing-branch audit commit. Keep the checkpoint intact for finishing-branch and preserve its separate integration authority.

Finishing-branch verifies the source closure with current gate/technical completion and no pending release review/audit, then prepares the actual destination, method, checks and authorized branch action. Preserve original phase/audit commits: use permitted fast-forward or preservation merges; incompatible squash/rebase policy blocks integration until a supported protocol is approved. Check the integrated SHA separately without rewriting/reclosing the historical source checkpoint. Reuse applicable authority; retain branch, PR open, verified integration, publication and deployment are distinct outcomes. Metadata timing, conflict/interruption recovery, and cleanup preserve reviewed state, evidence, local/ignored content and worktree ownership. The report references actual Git/platform results; it adds no controller integration fields or audit commit.

Draft the next required document, gain its approval, then proceed to dependent phases. Explicit user execution authorization may cover multiple phases; each phase still needs current task evidence, an independent Sol review, and a validated commit before the next phase. Approval to execute does not authorize push, merge, publication, or deployment. `$backlog` remains independent.

CLI shape: `python3 <plugin-root>/scripts/spec-flow.py --root <project> OP --input <json-file>`. Operations include `initialize`, `validate`, `digest`, `approve`, `gate`, `capabilities`, `start`, `authorize`, `prepare`, `restore-packet`, `bind-agent`, `result`, `verify`, `review`, `close`, `resume`, `reconcile`, `takeover`, `interrupt`, `phase-ready`, `review-phase`, `commit-phase`, `refresh-evidence`, `release-review`, `complete`, `status`, and the three migration operations. Resolve plugin root from the installed skill location. Follow the selected phase skill's own hard gate and stop on any failed gate.

## Runtime and approval

Resolve the plugin root from this installed skill. Run `python3 <plugin-root>/scripts/spec-flow.py --root <project> validate --input <json-file>` with `{"path":"<project-relative path>"}` after writing. Use `digest` with the same input to capture exact dependency digests. One fenced `spec-flow` JSON block holds `schema_version: 1`, `kind`, stable `id`, `revision: "R00"` initially, and `depends_on` references. Decision prose remains outside the block. Only generated progress and optional lowercase `status` may be updated as views.

The relevant document skill owns drafting and approval. Bootstrap does not itself approve or rewrite artifacts.

## Execution closure

The controller starts one explicitly authorized phase by default. Close tasks only after current checks and review; task closure does not commit or complete the run. At each phase boundary use `phase-ready`, obtain an independent Sol high review of the exact pinned tree with `review-phase`, then call `commit-phase`. The next dependent phase cannot start before the prior phase commit is in the current branch history. Once every declared phase has committed and `complete.technical_complete` is true, pass through `$converge` and `$review-release`; the latter calls `release-review` to write the derived technical outcome and roadmap reference and create the final audit-only commit. `complete` and `scripts/check-complete.sh <tasks.md>` are read-only evidence-and-commit checks; task checkboxes alone do not prove completion. If a bounded task or phase packet cache is missing, use `restore-packet` with the same run/owner and task or phase ID before resume/review; it only restores when approved source pins reproduce the event hash. Corrupt caches are not replaced, and older events without the original timestamp may be unrecoverable. Use the concrete payloads in [the execution contract](../../harness/contracts/execution.md).
